Hotel Booking Multi-Supplier Settlement Workflow

Architecture & Implementation Documentation

Overview

This document describes the current state of the multi-supplier booking and settlement system after two recent commits. The system enables multi-supplier reselling: a storefront tenant can discover and book another supplier's published inventory. When a guest pays for a booking from published inventory, two settlements are automatically created: one from the platform to the seller, and one from the seller to the inventory owner, with commission applied.

Workflow: From Inventory Publishing to Payment

1. Inventory Owner Publishes

A supplier publishes a room and rate plan via InventoryVisibility with:

  • Net rate: The owner's cost for the room
  • Markup cap: Maximum markup the seller can apply (storefront's markup is capped at this)
  • Commission percentage: What the owner earns as commission on top of net rate
  • Booking window: Min/max days ahead when the room can be booked
  • Visibility: Public (to all tenants) or reserved (for one specific tenant)
  • Status: Active, paused, or archived

2. Storefront Searches

Another tenant's storefront searches for properties via POST /b2c/search. The API returns:

  • The tenant's own inventory (if marked public to B2C)
  • Any inventory published to it by other suppliers

Only published room/rate-plan pairs are shown (not the entire property). Reserved terms override public ones when multiple records exist for the same pair.

3. Guest Reviews & Books

The guest calls:

  • POST /b2c/bookings/review: See the price without committing
  • POST /b2c/bookings: Create a booking

Search and booking share the same priceStay() function, so the price shown equals the price charged. Booking is refused if:

  • Check-in is outside the published booking window
  • The markup would not cover what the seller owes the owner
  • There is insufficient availability

4. Payment & Settlement Creation

The guest calls POST /b2c/bookings/:id/payment with their payment reference. In a single database transaction:

  • Booking status is atomically updated to "confirmed" (prevents double-payment)
  • Payment record is created
  • Both settlements are created (seller and inter-supplier)
  • Revenue transaction is logged
  • Audit entries are written

Important: If any step fails, all are rolled back. A second payment attempt on the same booking returns 400 and does not create duplicate settlements.

5. Settlement Visibility & Payment

The platform admin can view settlements by role:

  • GET /settlements/receivable: Inter-supplier settlements owed to the admin's tenant (where admin is the owner)
  • GET /settlements/payable: Settlements the admin's tenant owes (where admin is the seller)

Settlements progress: pending → paid (admin marks paid with MFA). Tier-2 settlements also get a 15-day due date and are marked overdue if unpaid after that.

6. Cancellation Handling

If a booking is cancelled before payment, the settlements are voided (status → cancelled). If a settlement was already paid, it is left as is and the revenue transaction is flagged "disputed" for manual recovery.

Key Implementation Details

Settlement Amounts

Guest Total = (Guest Rate × Nights) + 10% Tax

  • Guest Rate: Net Rate × (1 + min(StorefrontMarkup, PublishedMaxMarkup) / 100)
  • Seller receives: Guest Total − 2% Platform Fee − 3% Gateway Fee
  • Owner receives: (Net Rate × Nights) + (Net Rate × Nights × Commission%)
  • Validation: Seller must receive ≥ Owner amount; if not, booking is refused
Example (5 nights, net $150, 20% markup cap, 5% commission):
  • Guest rate = $150 + min(25%, 20%) × $150 = $180/night
  • Guest pays = $180 × 5 + 10% = $990
  • Seller receives = $990 − $19.80 − $29.70 = $940.50
  • Owner receives = ($150 × 5) + ($150 × 5 × 5%) = $787.50

Pricing Function: priceStay()

Located in stay-pricing.ts. Takes:

  • Calendar rates (array of daily net rates)
  • Markup percentage
  • Number of nights
  • Optional published terms (net rate, markup cap, commission)

Returns: net rate, sell rate, subtotal, tax, total amount, commission %, and sellable flag. Used by both search and booking so displayed price = charged price.

Search Integration

B2CSearchService.searchTenantInventory() returns:

  • Tenant's own public inventory
  • Inventory published to it

For each room/rate-plan pair, it loads calendar rates for the date range, applies priceStay() with published terms, and hides rows with availability < 1 or not sellable. No net rates or owner identity are exposed in search results.

Transactional Safety

Booking creation uses Prisma $transaction() to make payment confirmation and settlement creation atomic. The booking status field is checked before update; a second payment attempt returns 400 and does not create duplicate settlements.

Known Gaps & Next Steps

1. Payment is not verified. POST /b2c/bookings/:id/payment accepts any reference from anyone who knows the booking ID and email. Must be replaced by a verified gateway webhook before launch.
2. Booking site is untested with published inventory. The API returns it correctly, but the frontend has not been run against it and falls back to mock data on failure.
3. No inventory capacity tracking. Creating or cancelling a booking does not reduce the room count in the calendar; availability is advisory only.
4. Cancellation is partial. Cancellation penalties are not split between seller and owner, paid settlements are not reversed, and chargebacks are not handled.
5. Demo bookings still exist. If a storefront cannot sell a property, booking creation stores a $275 placeholder that never creates settlements. Should be removed.
6. Rate limiting is configured but not enforced.
7. MFA is optional. Settlement endpoints require a code in the header, but do not require the user to have MFA enabled.
8. Tenants have no inventory management UI. All publishing, pausing, and term updates happen via API or database only.

Recommended Next Steps

  1. Implement payment gateway webhook verification (Stripe, etc.) before launch
  2. Test the frontend against published inventory and fix fallback behavior
  3. Add inventory capacity management (room count, reservation blocking)
  4. Implement cancellation penalties and refund logic
  5. Remove demo bookings when storefront has a fallback flow
  6. Build a supplier tenant UI for managing published inventory and rate terms
  7. Enforce rate limiting on settlement endpoints
  8. Set up monitoring and alerting for settlement creation and payment failures

Environment & Configuration

Required

ENCRYPTION_KEY: 64 hex characters (set in .env). Used for storing MFA secrets and PII encryption. No fallback; service throws on startup if missing.

Optional

  • Database must be synced with Prisma schema (pnpm db:push)
  • API runs on port 3001 in dev mode
  • Frontend falls back to mock data if API is unavailable

Summary

The system now supports end-to-end multi-supplier reselling: published inventory appears in storefronts, bookings are priced consistently, and settlements are created atomically with payment. Security includes MFA on settlement operations, AES-256-GCM encryption for secrets, and audit logging. Test coverage spans unit tests, integration checks, and smoke tests. Before launch, payment verification and inventory capacity tracking must be added.
